# Вход, права и переход на Бизнес

Состояние реализации и проверка документации: **18 ноября 2026**. Код: `app/auth.py`, `app/billing.py`, `app/core.py`. У приложения нет формы для пароля Яндекса или Госуслуг. API провайдера вызывается только из backend; для рабочего входа пользователь открывает сайт как самостоятельную HTTPS-страницу, не в iframe.

## Подготовить рабочее окружение

1. Разместите приложение, хранилище и резервные копии в согласованной инфраструктуре в РФ. Не используйте публичное демо-превью для ПДн.
2. Закончите [проверку оператора](personal-data.md). Опубликуйте на доступных без входа HTTPS-страницах **свою** политику и **отдельное** согласие, архивируйте редакции. Заполните `POLICY_URL`, `CONSENT_URL`, `CONSENT_VERSION`, `OPERATOR_CONTACT`. `/privacy` и `/consent` в демо — пояснения к стенду, не готовые документы организации.
3. В отдельном проекте/томе задайте `APP_MODE=production`, `PUBLIC_URL=https://cabinet.example.ru` (ваш origin, без пути и завершающего слеша). Сгенерируйте `APP_SECRET` из 32 случайных байт, например `python -c 'import secrets; print(secrets.token_hex(32))'`. Не вставляйте его в JS. Храните резервную копию секрета отдельно от тома. Его потеря нарушит поиск идентичностей; менять нужно по плану миграции, а не при каждом деплое.
4. Терминируйте TLS на доверенном reverse proxy без кеширования `/api`. В контейнер проксируются `/` и `/api` одного origin. Не открывайте Gunicorn напрямую в сеть. Контроль `Host`, ограничения запросов/размера, TLS-сертификат и доверенные адреса proxy — ответственность периметра. Для `/api/auth/*/callback` исключите query string из логов. Не логируйте тела `/auth`, заголовки Cookie/Authorization, SMS и ответы провайдеров.
5. Включите хотя бы один способ входа ниже. Запустите `docker compose -p buro-prod up --build -d --wait`. Если демо уже занимает 8080, поменяйте `PORT`. Отсутствие обязательной конфигурации блокирует запуск, отсутствие отдельного провайдера отключает соответствующую кнопку. Нет общего предустановленного пользователя.

### Яндекс ID: прямой OAuth Authorization Code + PKCE

- Создайте веб-приложение в [кабинете Яндекс OAuth](https://oauth.yandex.ru/). Разрешите **точный** Redirect URI `https://cabinet.example.ru/api/auth/yandex/callback` и право `login:info`. Не запрашивайте дату рождения, e-mail, телефон или аватар «на будущее».
- Положите идентификатор и пароль приложения в `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`.
- **Реализовано:** `POST /api/auth/yandex/start` создаёт связанный с анонимной сессией одноразовый `state` и `code_verifier`. Браузер переходит на `https://oauth.yandex.ru/authorize` с `response_type=code`, точным `redirect_uri` и `code_challenge_method=S256`. Callback сверяет сессию и срок и потребляет state **до** обмена кода. Backend отправляет `code`, verifier и аутентификацию клиента в `https://oauth.yandex.ru/token`.
- Backend запрашивает `https://login.yandex.ru/info?format=json` с `Authorization: OAuth …`, проверяет `client_id`, берёт `id`. Профиль/токены не сохраняются; ключ поиска — HMAC от пространства провайдера, клиента и идентификатора. Имя для кабинета выбирает сам владелец. Повторный вход не перезапускает демо-период.

Источники: схема и параметры кода [2](https://yandex.ru/dev/id/doc/dg/oauth/reference/auto-code-client.html), PKCE S256 и обмен [1](https://yandex.ru/dev/id/doc/en/codes/screen-code), [формат профиля и заголовок OAuth](https://yandex.ru/dev/id/doc/ru/user-information).

### Госуслуги: ЕСИА через выделенный доверенный OIDC-брокер

**Граница интеграции:** приложение — OIDC-клиент брокера организации, не прямой клиент криптографического интерфейса ЕСИА. `ESIA_ISSUER` **не** равен `gosuslugi.ru`. Произвольный малый бизнес не получает промышленный доступ только благодаря наличию кнопки. Сначала проверьте основание подключения своей ИС, зарегистрируйте её на технологическом портале, оформите тестовый и затем промышленный допуск, согласуйте scope и зарегистрируйте сертификат ИС. Порядок регистрации и заявок — на Госуслугах [1](https://info.gosuslugi.ru/articles/%D0%9A%D0%B0%D0%BA_%D0%BF%D0%BE%D0%B4%D0%BA%D0%BB%D1%8E%D1%87%D0%B8%D1%82%D1%8C%D1%81%D1%8F_%D0%BA_%D0%95%D0%A1%D0%98%D0%90/).

1. Используйте согласованный шлюз или отечественный IdP с внешним поставщиком ЕСИА, например **Blitz Identity Provider**. На его стороне настраиваются среда ЕСИА, мнемоника ИС, зарегистрированные ключи, подпись запросов по применимой версии протокола и проверка ответа ЕСИА. Не подставляйте строковый «client secret» вместо электронной подписи. Схемы и версии подключения различаются: техническое решение [3](https://info.gosuslugi.ru/upload/iblock/74f/yabemt58tul28c116stnt030g4xf9u92/Tekhreshenie_new.pdf), настройка внешнего поставщика [1](https://docs.identityblitz.ru/latest/only_in_russia/external-idp-domestic.html), подключение веб-приложения к IdP [2](https://docs.identityblitz.ru/5.23/integration-guide/oidc-web.html). Шлюз, его лицензия, криптопровайдер и закрытый ключ ЕСИА **не входят** в образ Бюро.
2. У брокера зарегистрируйте **confidential web client** для Бюро: только Authorization Code, PKCE S256, `client_secret_basic`, `scope=openid`; точный callback `https://cabinet.example.ru/api/auth/esia/callback`. Нужны HTTPS discovery по `ISSUER/.well-known/openid-configuration`, JWKS и подписанный **RS256** ID token с `nonce`. Это договор интерфейса **между Бюро и брокером**; RS256 не заменяет ГОСТ на участке брокер ↔ ЕСИА.
3. Политика клиента должна разрешать **только фактический вход ЕСИА**, не пароль/другую соцсеть брокера. Настройте подписанный строковый claim источника (`idp=esia` по умолчанию), вычисляемый из аутентификационного контекста, а не из редактируемого атрибута профиля. `sub` должен быть стабилен и однозначно связан с учётной записью ЕСИА. Если конкретная услуга требует подтверждённой УЗ/полномочий представителя организации, проверяйте это в политике шлюза: сам вход не подтверждает право действовать от юрлица.
4. Задайте `ESIA_ISSUER` в **точности** как поле `issuer` метаданных, `ESIA_CLIENT_ID`, `ESIA_CLIENT_SECRET`, при необходимости `ESIA_SOURCE_CLAIM` и `ESIA_SOURCE_VALUE`. Не смешивайте тестовый и рабочий issuer/клиент. Проверьте поддержку всех перечисленных возможностей вашей установкой брокера.
5. **Реализовано:** старт с PKCE/state/nonce, серверный обмен, проверка подписи по `kid` из доверенного JWKS, фиксированный алгоритм, проверки `iss`, `aud`, `azp`, `exp`, `iat`, `sub`, `nonce` и источника. Ошибка любой проверки завершает вход без выдачи сессии. У нас остаётся только HMAC от issuer + sub; паспорт, СНИЛС, цифровой профиль не запрашиваются.

### По номеру телефона: одноразовый код SMS.RU

- Подключите SMS.RU для сервисных сообщений, согласуйте отправителя, тарифы и обработку данных. Задайте `SMS_API_ID`. Протокол отправки и **статус каждого номера**, а не только общий ответ: [1](https://sms.ru/api/send).
- В этой версии принимаются российские мобильные номера формата `+79…` или `89…`; ввод нормализуется. Телефон нужен в открытом виде только на время отправки. `POST /api/auth/phone/request` создаёт случайный шестизначный код, отправляет через HTTPS POST. В БД — HMAC нормализованного номера и HMAC кода с уникальным id попытки. Код действителен **5 минут**, не более **5 ошибочных проверок**; новый запрос в этой сессии заменяет старый.
- Ограничения выдачи: не чаще раза в минуту и пяти запросов в час на номер, 60 запросов в час на адрес соединения. Атомарные счётчики в SQLite не сбрасываются рестартом. За proxy IP-лимит может быть общим: настройте отдельные лимиты на доверенной границе, не доверяйте произвольному `X-Forwarded-For`. Установите лимит расходов у SMS-провайдера.
- `POST /api/auth/phone/verify` проверяет код в породившей его сессии. При успехе попытка потребляется и session id меняется. Нет отправки «из браузера», логов кодов или универсального кода. Если SMS не принято, попытка отзывается. SMS подтверждает владение номером **сейчас**, не личность по паспорту. Для смены номера/перевыпуска SIM нужен отдельный регламент повторной проверки; автоматического переноса между номерами нет.

### После входа: права и онбординг

Владелец определяется по серверной сессии (`HttpOnly; Secure; SameSite=Lax; Path=/`), абсолютный срок 7 дней; анонимная сессия — 30 минут. Cookie содержит случайные 256 бит, в БД только HMAC. Успешный вход вращает токен; выход отзывает его. При смене `CONSENT_VERSION` доступ к рабочему кабинету требует подтверждения новой редакции. В домене провайдера пользователь при этом может остаться авторизованным. Изменяющие запросы требуют JSON и специального same-origin заголовка; CORS не включён, в production проверяется переданный Origin. `state` одноразов, живёт до 10 минут и привязан к сессии и провайдеру.

Владелец в URL или JSON не принимается. Все выборки/изменения бизнес-данных ограничены `account_id` сессии. Похожее имя, совпадение почты и номера из чужого профиля **не объединяют аккаунты**. Для настоящего linking нужен отдельный подтверждённый вход обоими способами. Совместной работы сотрудников/ролей команды пока нет.

Только в демо дополнительно допускается табовый идентификатор в `sessionStorage`: это позволяет работать в превью, где сторонние cookie заблокированы. Production его не выдаёт и игнорирует. Никогда не размещайте демо и production на одном origin.

При первом входе владелец выбирает одну или несколько целей. Backend валидирует их по списку, сохраняет профиль целей и создаёт соответствующие задания в одной транзакции. Уникальный ключ шаблона исключает дубли при повторном выборе; уже созданные задачи при изменении целей не удаляются.

## Оплата: редирект в ЮKassa, не форма карты в кабинете

1. Подключите магазин, заполните `YOO_SHOP_ID`, `YOO_SECRET`. До реальных списаний проверьте оферту, возвраты, налоги и применимость 54-ФЗ. Этот MVP не фискализирует операции сам: если нужны чеки, настройте кассовое решение и передачу требуемых реквизитов **до** приёма денег. Сценарии передачи чеков: [2](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/other-services/payments).
2. `POST /api/billing/checkout` принимает выбор Бизнес и подтверждение, но **не цену и не статус платежа**. Сумма задаётся на сервере: 99 000 копеек. `pending`-заказ создаётся в БД до сетевого вызова. В ЮKassa отправляется `POST /v3/payments` с `capture=true`, `amount`, `metadata.order`, `confirmation.type=redirect` и фиксированным `return_url`. В браузер передаётся ссылка на платёжную страницу провайдера.
3. Один незавершённый заказ на кабинет, id заказа — `Idempotence-Key`. При потере ответа повторяется тот же запрос с тем же ключом. API ЮKassa обеспечивает идемпотентность в течение 24 часов [1](https://yookassa.ru/developers/using-api/interaction-format). Через 23 часа заказ с неопределённым результатом создания требует ручной сверки в магазине, а не автоматического повторного списания.
4. **Возврат браузера не доказывает оплату.** На странице тарифа выполняется `POST /api/billing/check`. Сервер запрашивает `GET /v3/payments/{external_id}` с учётными данными магазина. Условия активации: `succeeded`, `paid=true`, `test=false`, совпадают id платежа, магазин, id локального заказа, сумма и RUB. В одной транзакции фиксируются успех и 30 дней доступа. Повторная проверка не продлевает доступ дважды. `canceled` не активирует тариф. Данные клиентов при смене тарифа не копируются и не сбрасываются.
5. Даже если пользователь закрыл вкладку, сервис `maintenance` из Compose сверяет известные внешние id каждые две минуты. Вручную: `docker compose exec -T cabinet flask --app wsgi reconcile`. Проверяйте логи `maintenance` и оповещения об ошибках. Webhook, которому можно было бы передать произвольный `succeeded`, не предусмотрен. Все внешние вызовы — вне пишущей транзакции и с таймаутом. Возвраты и споры обрабатываются оператором в магазине с последующей сверкой права доступа; автоматизации возвратов нет.

## Приёмка до публикации

- В новом браузере без сессии production показывает вход. Отказ у провайдера, неверный state, чужой issuer/nonce/источник, просроченный или повторный код не открывают кабинет.
- Протестировать каждого реального провайдера на согласованном стенде, возврат на точный HTTPS callback, повторный вход в тот же кабинет, выход, ротацию ключей брокера. Модульные тесты с подменой транспорта **не заменяют** приёмку у провайдера.
- Проверить отчёт магазина и сверку успешной/отменённой операции. Продуктивный обработчик намеренно не активирует Бизнес по тестовому платежу. Для локального прохождения всего пути используйте `demo`; не ослабляйте проверку `test=false` в production.
- Сверить с владельцем продукта сроки, лимиты, цену, текст документов и процедуру восстановления. Отключить все ненастроенные способы. Не использовать тестовый номер, стендовые токены и демоданные в рабочей БД.
