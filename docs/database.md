# База клиентов и границы нагрузки

## Какой запас по числу аккаунтов?

**Проверено 10 000 учётных записей** на одном экземпляре приложения при **12 одновременно выполняемых HTTP-запросах** и небольшом количестве данных на владельца. В этом профиле 95% ответов API укладывались примерно в **27 мс**. Это измеренный ориентир для старта, не «предел SQLite» и не обещание для 10 000 одновременно работающих пользователей.

### Воспроизводимый эксперимент, 18.11.2026

Рабочий путь `production` с синтетическими клиентами и сессиями (проверяются владелец, срок и версия согласия), Gunicorn 1 worker × 4 threads, Python 3.11, SQLite 3.40.1, Linux x86_64, 2 vCPU, около 3,8 GiB RAM, локальная файловая система виртуальной машины. Генератор и сервер на одной машине. Тип и гарантированные IOPS физического накопителя не измерялись.

| Аккаунтов | Карточек клиентов | Задач | Размер основной БД | p50 | p95 | p99 | Запросов/с | Ошибок |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 000 | 12 000 | 4 000 | 2,1 MiB | 20,31 мс | 26,23 мс | 31,92 мс | 582,2 | 0 / 1 200 |
| 10 000 | 120 000 | 40 000 | 20,4 MiB | 20,71 мс | 26,89 мс | 38,25 мс | 561,9 | 0 / 1 200 |

`python scripts/benchmark.py --accounts 10000 --requests 1200 --concurrency 12` создаёт **временную** БД: на каждого владельца профиль, идентичность, сессия, согласие, 12 клиентов, 4 задачи и 3 события. Стартует локальный Gunicorn на временном loopback-сокете. После 20 запросов прогрева измеряются 1 200 запросов со случайным равномерным выбором аккаунтов: 90% — `GET /api/workspace` со сводкой и статистикой, 10% — `PUT /api/tasks/:id` с записью статуса и события. Время включает HTTP по loopback, проверку сессии, SQL и JSON; запросы выполняются без пауз. Скрипт останавливает процесс и удаляет тестовые данные. Для первой строки замените `--accounts` на `1000`.

**Что это не измеряет:** географическую задержку, отрисовку, SMS/OAuth/оплату, холодный кеш, продолжительную запись, пик на одном «горячем» аккаунте, работу при полном диске и одновременном backup. Небольшая разница p95 между строками — недостаточное основание для линейной экстраполяции на большую базу. Показанные RPS не являются рекомендуемой постоянной нагрузкой.

Для своего решения «без лагов» сначала задайте SLO, например p95 внутреннего API ≤ 200 мс, p99 ≤ 500 мс и отсутствие `SQLITE_BUSY` на целевой смеси запросов. Повторите тест на **том же типе тома**, затем длительный прогон с реальными размерами базы, пиками записи, checkpoint и резервным копированием. Пустые 100 000 аккаунтов и 100 интенсивно пишущих — совершенно разная нагрузка.

## Сущности и связи

Источник истины — [`app/schema.sql`](../app/schema.sql), `PRAGMA user_version=1`. Время — секунды Unix UTC, отображение дат — локаль браузера, деньги — целые копейки. Учётная запись владельца сервиса и клиент его бизнеса — **разные сущности**.

```text
identities ──N:1── accounts ──1:N── clients         карточки клиентов бизнеса
                    │       └─1:N── tasks           свои и рекомендованные задачи
                    │       └─1:N── events          история без имён/телефонов в тексте
                    │       └─1:N── payments        заказы и подтверждения
                    │       └─1:N── consents        принятые версии
                    │       └─1:0..1─ holds         блокировка оператором
                    └───────1:N── sessions ──1:N── challenges
                                  ↑ у анонимной сессии account_id = NULL
meta: режим базы                     rate_limits: HMAC ключа, счётчик, срок окна
```

| Таблица | Назначение и инвариант |
|---|---|
| `accounts` | Авто-id, отображаемое имя и компания, JSON-массив разрешённых `goals`, этап профиля, момент создания, `trial_until`, `paid_until`, последний способ входа, прочитанные уведомления. Тариф выводится из **серверного** времени, а не из флага браузера. |
| `identities` | Составной PK `(provider, subject)`; `subject` — HMAC, отдельные пространства имён телефона, Yandex client/id и ESIA issuer/sub. Это псевдонимизация, не анонимизация. |
| `sessions`, `challenges` | PK HMAC сессии, срок, FK владельца; попытка входа связана с конкретной сессией и провайдером, содержит срок, счётчик, версию согласия, HMAC кода **или** временный PKCE verifier и nonce. Каскадное удаление при отзыве сессии. |
| `clients` | `id`, обязательный FK владельца, имя, необязательные компания и почта, дата. Индекс `(account_id,created DESC,id DESC)`; поиск ограничен кабинетом, страницы по 20. |
| `tasks` | Заголовок, категория, флаг выполнения с `CHECK`, шаблон и дата. `UNIQUE(account_id,template)` для задач онбординга; индекс владельца и статуса. |
| `consents` | PK владелец + версия, дата и способ подтверждения. Оператор хранит **неизменяемый текст редакции отдельно**, не заменяет документ на том же URL без смены версии. |
| `payments` | UUID — и id заказа, и ключ идемпотентности; копейки, валюта фиксирована RUB, статус с `CHECK`, уникальный внешний id, ссылка подтверждения, дата. Не более одного `pending` на владельца (частичный уникальный индекс). FK `RESTRICT` не позволяет незаметно стереть финансовые записи с аккаунтом. |
| `events`, `holds`, `rate_limits`, `meta` | Индекс истории по владельцу/id. Блокировка отзывает сессии. Ограничители выдачи переживают рестарт. Маркер режима предотвращает случайное использование демо-базы в production. |

Новое право по тарифу и платёж фиксируются вместе; создание задачи и запись истории — вместе. Операции ввода-вывода к провайдерам не держат пишущий lock. Согласие, создание пользователя и привязка личности атомарны. Параметризованные запросы не принимают таблицу, владельца или цену из данных клиента.

## Конфигурация и когда менять СУБД

- Одна БД на **локальном** томе одного хоста, один экземпляр сервиса. `foreign_keys=ON` на каждом соединении, `journal_mode=WAL`, `synchronous=NORMAL`, ожидание блокировки до 4 с, `BEGIN IMMEDIATE` для связанных изменений. Соединение принадлежит контексту запроса; нет глобального соединения, разделяемого потоками. `NORMAL` — осознанный компромисс: после сбоя питания последние зафиксированные изменения могут быть утрачены. Для иных требований к долговечности оцените `FULL`, надёжное хранилище и повторите замеры.
- WAL позволяет чтению сосуществовать с записью, **писатель в конкретный момент один**. Много одновременно регистрирующихся/платящих клиентов, массовые импорты и долгие транзакции важнее размера реестра. WAL не предназначен для общего сетевого файла на нескольких машинах. Рекомендации SQLite [2](https://www.sqlite.org/whentouse.html), [документация WAL](https://www.sqlite.org/wal.html).
- Лимиты **продукта**, не движка: демо — 100 клиентов / 30 задач на кабинет, Бизнес — 2 000 / 500. CSV только при действующем платном доступе. История и списки постраничные; поиск по подстроке сканирует записи **конкретного владельца**. Остаток диска, размер WAL и время checkpoint нужно наблюдать.
- Если p95 выходит за SLO, появляются регулярные 503/`SQLITE_BUSY`, требуется несколько реплик приложения на разных узлах, HA, тяжёлая аналитика или массовые импорты — планируйте PostgreSQL. Не лечите это `docker compose --scale` с тем же SQLite на NFS.
- Путь миграции: остановить изменения/сверку, сделать согласованную копию, перенести таблицы в порядке FK с сохранением id и уникальностей (в т.ч. частичного индекса pending), перенести HMAC-секрет безопасным каналом, проверить суммы и сроки/количества/связи, пересверить pending в магазине, выполнить нагрузочный и приёмочный тест, затем переключить приложение. Нужны отдельная реализация слоя доступа и миграции; смены `DATABASE` на URL недостаточно.

## Эксплуатация

**Данные:** `/data/buro.sqlite`, файлы `-wal` и `-shm` в именованном томе `cabinet-data`. Не копируйте только основной файл на работающем сервисе. У контейнера нет root-доступа, но SQLite по умолчанию **не шифрует** ФИО, почту и профиль. Используйте зашифрованное блочное устройство, закрытые права и шифрование резервных копий. Не помещайте копии в Git.

Пример согласованной online-копии (выполнять из закрытого каталога на хосте в РФ):

```sh
umask 077
stamp=$(date -u +%Y%m%dT%H%M%SZ)
docker compose exec -T cabinet flask --app wsgi backup "/tmp/buro-$stamp.sqlite"
docker compose cp "cabinet:/tmp/buro-$stamp.sqlite" "./buro-$stamp.sqlite"
docker compose exec -T cabinet rm "/tmp/buro-$stamp.sqlite"
```

CLI использует SQLite Backup API и отказывается перезаписывать существующую копию. Защищайте `APP_SECRET` отдельно; в демо идентификационный ключ `demo.key` тоже нужен для продолжения старых сессий. **Восстановление:** не раскатывать поверх живых файлов. Остановить запись и планировщики, развернуть отдельный чистый том, при остановленном сервисе положить копию как `/data/buro.sqlite` (владелец UID 10001, права 0600), без старых `-wal/-shm`. Использовать соответствующие режим и секрет; проверить `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, карточки/тарифы и сверку заказов. Отозвать старые сессии и challenges; применить журнал удалений после даты копии **до** открытия доступа. Тренировать восстановление и измерять RPO/RTO. Для версии схемы, отличной от поддерживаемой, приложение не запускается: перед обновлением нужна проверенная миграция и копия.

**В Compose уже есть `maintenance`:** в том же локальном томе выполняются очистка при старте/раз в сутки и сверка с магазином каждые две минуты. Не запускайте второе расписание параллельно. Команды ниже — для ручного повторения или запуска без Compose. Резервирование, ротацию и контроль сроков рабочих данных настраивает оператор.

| Частота (пример) | Команда | Назначение |
|---|---|---|
| Ежедневно | `docker compose exec -T cabinet flask --app wsgi cleanup` | Удалить истёкшие sessions, challenges, rate_limits, историю старше 90 дней и **только в demo** кабинеты старше 30 дней. Истёкшие токены непригодны ещё до очистки. |
| Каждые 2 мин в production | `docker compose exec -T cabinet flask --app wsgi reconcile` | Проверить pending с известным id в магазине, независимо от браузера. Повторная обработка безопасна. Оповещать оператора о ненулевом коде выхода. |
| По утверждённым RPO/срокам | `backup` + перенос/шифрование/ротация | Копии на отдельном защищённом носителе в РФ; политика удаления распространяется и на копии. |

Для рассмотрения запросов субъектов есть **только локальные** административные команды `hold-account ID` (отзывает сессии, запрещает повторный вход), `release-account ID` (требуется войти заново), `erase-account ID` (требует блокировку и подтверждение). Запускать через `docker compose exec cabinet flask --app wsgi …` после проверки полномочий; их не должно быть в публичном API. Удаление отказывается удалять аккаунт с платежами: сначала примените отдельно утверждённый регламент финансового хранения/минимизации. Эти команды не заменяют учёт обращений, акты уничтожения и обработку резервных копий.
